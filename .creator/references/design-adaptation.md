# Project design adaptation

Use for an authorized request to establish, adapt or enrich project design rules. This is the shared procedure for the creator gateway, design-brief-builder and project-knowledge; it is not a second design system. Ordinary UI work follows [project-design.md](project-design.md).

## Inputs and responsibility

Establish the target project, requested pages/tasks, writable scope and intended output. Read existing current state, design entry and conditional references, effective decisions, local exceptions, relevant components/tokens and working-tree changes. Preserve the project's language and equivalent filenames. Do not infer a redesign from a request to organize rules.

The gateway selects this route and locates its bundled `design-library/README.md` (in the source checkout, the sibling top-level design-library). Read the index and selected modules only. Design-brief-builder owns design decisions; project-knowledge reconciles their authoritative documents. If those skills are installed and consistent with this contract, use them. Otherwise the gateway performs this same procedure; absence of an installed workflow does not authorize installing it or prevent an authorized document-only adaptation.

The library is optional authoring evidence. Use the user-selected trusted source/package, record the revision actually read, and inspect suitability. Do not install third-party skills or fetch changing “latest” rules on every UI task. If the library is unavailable, disclose the evidence gap, use available project evidence for independent work and do not pretend a library-assisted adaptation occurred.

## Select and adapt

1. Map actual surfaces and user tasks. One repository may contain operational settings, an editor, a public site and documentation. Select the smallest relevant modules plus foundations as needed; do not select by industry label or load every module.
2. For each affected topic classify the current rule: keep, fill a demonstrated gap, merge duplication, or resolve a conflict. Mature adequate rules can produce a justified no-change result. Do not equate “not in the library” with wrong.
3. Turn suitable suggestions into project-specific decisions: scope, intended user behavior, existing component/token mapping, important exceptions, and observable checks. Use concrete available names; unknown implementation details stay identified, not fabricated. Do not copy whole modules, examples, all alternative branches or unresolved placeholder checklists into the active rules.
4. Preserve effective conventions even when a library example differs. User decisions take precedence; observed code is evidence, not automatic approval. Ask only for a necessary unresolved experience, cost, privacy or authority choice. Cosmetic and technical details with adequate context are autonomous. Continue unaffected portions while a consequential choice remains open.
5. Keep defaults, save semantics, permissions and required functions within authorization. Improving a document does not add auto-save, telemetry, authentication providers, dependencies or new product features. A new guideline is an intended requirement, not proof the UI implements it.

## New project output

Create the smallest local design owner adequate for the known scope; use the project's requested name, otherwise the workflow's Design-Brief default. Record users/tasks and constraints, adopted layout/component/content/state rules, decisions still genuinely unresolved and relevant acceptance. Link it from the existing current-state entry or use an existing design registration mechanism; no new state-schema field is mandatory.

If there are no actual components or tokens, propose bounded starting roles under the authorized design scope and mark them as proposed/not implemented. Do not invent an installed library. Split topic documents only when separate audiences or substantial content justify it; support one document with sections first.

## Existing project merge

Edit the existing topic owner, preserving unrelated text and working changes. Follow [project knowledge](project-knowledge.md) for sources, status and replacement. Revise superseded active clauses in place rather than appending the opposite instruction. Preserve historical evidence and intentional exceptions; do not infer removal from age, absent implementation or generic advice.

Show a concise change summary: preserved choices, actual additions, resolved replacements and remaining consequential conflicts. Keep unique useful detail. Only update references and the current-state entry when their meaning changes. Respect a narrower user file scope; report a necessary follow-up instead of editing read-only files.

## Adoption and later updates

In the existing document, a brief source note is sufficient: selected module names and revision, applicable scope, meaningful local overrides, and date/reason where it helps future reconciliation. A source citation is provenance, not a dependency requiring developers to load the original module. Active project rules must contain the adopted decisions or link to other active local owners.

Library upgrades provide new candidates only. On a later authorized adaptation, compare the last adopted basis (if available), current local rules and relevant new suggestions. Preserve local amendments; an unknown original basis is not permission to replace. Do not maintain a second generated master file beside an established project owner or build a mandatory per-rule ledger.

## Acceptance and handoff

- Target scope and existing conventions are recoverable; irrelevant scenes and unresolved alternatives have not become active rules.
- New or changed clauses explain this project's actual choice and acceptance, not just “modern”, “clean” or copied library prose.
- Existing rules and exceptions survive unless a valid replacement decision exists; references resolve and no contradictory active duplicate remains.
- The project design entry leads to the adopted rules without requiring the authoring library. Daily work can proceed if the gateway/library is absent or later changes.
- Report documents changed (or a justified no-change), adopted sources, conflicts and evidence. Separate document checks from application implementation, visual validation, installation and publication.

Validate scope and local links, then inspect meaning. Do not run business flows merely to prove a document merge, and do not declare UI compliance from source selection. Installation remains the ownership-aware installer's separate responsibility.
