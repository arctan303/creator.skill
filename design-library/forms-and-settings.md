# 表单与设置：输入、草稿和生效边界

> 参考材料，未采纳不生效。本文供设计适配阶段选择适合项目的表单规则；日常开发只使用项目已采纳准则，不直接继承本库。

适用：填写资料、偏好设置、插件配置、连接参数，以及已有表单的布局与反馈改进。
不适用：替代业务校验契约、凭视觉偏好重定义字段类型，或给已有批量提交流程自动增加即时保存。
以下默认建议只用于有选择空间的设计；已有字段类型、接口语义和整体 Save 契约应保留，除非用户已授权相应产品变更。
**不采用“所有字段无条件自动保存”的规则。原位编辑并不等于自动保存。**

## 先画出生效边界

适配时先明确：哪些值只是草稿，何时提交，是否整体校验，失败如何处理，以及取消到底撤回什么。
这是控件与布局的输入；不能先选一排漂亮的开关，再让接口被迫即时提交。

| 场景 | 可选方案 | 理由与代价 |
| --- | --- | --- |
| 多字段互相依赖，已有整体保存 | 原位表单与统一 Save/取消区 | 保留一次校验与一次提交；需要明确脏状态 |
| 独立可逆设置，产品已允许即时提交 | 即时控件、局部等待和失败反馈 | 快速完成单项任务；取消不能声称撤回已保存值 |
| 少数普通设置，目前重复摘要加弹窗 | 原位展示可编辑字段，保留提交语义 | 减少一次无意义跳转；别同时改控件类型和保存时机 |
| 概览优先，少数角色可编辑 | 摘要加明确编辑入口 | 便于阅读与权限表达；需要真实的概览价值 |
| 复杂连接或独立编辑事务 | 页面、分步流程或有理由的弹窗 | 容纳依赖与核验；增加路径需体现任务边界 |

同一可见区域内可同时存在整体保存与即时操作，但两者需要明确分区、动作名称和状态归属。
例如“重新测试连接”是独立动作，不应该被统一 Save 偷偷触发；已发出的测试也不由“取消修改”撤回。
离开、关闭、刷新时的草稿处理沿用项目契约；本参考不自动增加跨页草稿或恢复能力。

## 选择控件，保留类型语义

先查项目的字段模型、实际数据和组件；下表是新设计的候选，不是给旧字段强制迁移的命令。

| 输入意图 | 默认候选 | 需要检查 |
| --- | --- | --- |
| 多项选择、确认声明、随表单提交的布尔值 | Checkbox | 组名、是否可多选、草稿是否清楚 |
| 已允许即时生效的可逆二元状态 | Switch | 真实结果、等待、失败恢复及正向标签 |
| 少量互斥项，需要同时比较 | Radio / 既有单选按钮组 | 唯一选中状态、键盘行为、选项说明 |
| 较长或动态单选列表 | Select；必要时可访问 Combobox | 选项量、搜索价值、空结果、键盘与读屏 |
| 连续量与近似调节 | Slider，必要时带精确输入 | 单位、范围、步长与键盘操作 |
| 精确标识、金额、地址、密码等 | 语义相符的输入字段 | 保留类型、格式、精度和安全边界 |
| 执行命令或导航 | Button / Link | 不用状态开关代替删除、重连或跳转 |

已有开关随整体 Save 提交，是项目可以保留的明确例外；通过保存区、未保存状态和文案解释草稿，不擅自换成另一种提交方式。
也不要为了“控件统一”把 select 改成文本、把布尔值改成字符串，或减少原本可选的值。
少量选项是否展开，需要考虑比较价值与空间；“永远不用下拉”和“全部改搜索框”都缺少场景依据。
标签表达对象或正向含义，选项表达真实值；避免开关标签随状态翻转，使用户无法判断当前事实。

## 分组、条件字段与帮助

普通填写可从单列、标签在上开始；紧凑设置可采用左标签右控件，同类行保持稳定对齐。
关系紧密且空间充足的字段可以并列；窄屏按理解顺序堆叠，错误仍靠近自己的字段。
统一标签、值与按钮的文字角色；帮助文字不是另一套随机字号，错误出现时也不改变字段归属。
分组按用户任务组织，例如“接收消息”和“发出通知”；不要机械按字符串、数字、布尔类型分组。
字段标签不由 placeholder 代替；组内选项有可理解的组名和必要的多选说明。
帮助只补充格式、范围、影响与例外；不为每个字段补一句“请输入你的……”或加一个不可触达的悬停提示。
必要的权限、费用和数据去向就近可见；高级帮助可以展开，不能把完成当前操作所需的信息一起藏起来。

| 条件变化 | 适配时要明确的项目规则 | 默认倾向及理由 |
| --- | --- | --- |
| 选项开启后出现相关字段 | 出现位置、键盘顺序、当前错误归属 | 放在控制项附近，减少寻找 |
| 字段暂时不适用 | 隐藏或禁用、是否参与校验 | 依据任务理解，不能只为减少高度选择 |
| 隐藏字段已有值 | 保留、清除或提交时忽略 | 保留已有数据契约，不因收纳而清除配置 |
| 选择会影响费用或权限 | 提示与提交边界 | 决策前可见，不能只在失败后补充 |

## 保存、验证与关键状态

保存动作说明范围，例如“保存通知设置”；页面已有清楚范围时可以只用“保存”，不必每处写成长句。
提交中防止重复请求，同时让用户知道正在处理；不要把请求发出当成成功。
失败保留可修复草稿，并说明字段问题、服务故障或权限变化；这些问题不能全部标成“格式错误”。
验证通常在用户尝试继续或提交时完整执行；提前验证只在能减少返工、不会持续打断输入时采用。
错误同时说明问题与可行修改，避免只有“无效”；大型表单可以增加可聚焦摘要并链接对应字段。
必要格式可提前说明，但不把每个内部实现限制变成说明段；能容忍无歧义格式的输入不应无故拒绝。

| 状态 | 用户能观察到什么 | 防止的误导 |
| --- | --- | --- |
| 初始与未修改 | 当前已保存值、编辑权限、正确默认 | 空字段被误当成“从未设置” |
| 已修改未保存 | 草稿边界及实际可用的保存/取消 | 开关变化被误当成已经生效 |
| 提交中 | 范围明确的等待反馈 | 重复点击造成多次提交 |
| 保存成功 | 已保存事实及必要的生效条件 | 仍需重启却宣称全部生效 |
| 字段错误 | 就近错误与保留的输入 | 用户失去草稿并重新填写 |
| 请求失败或权限变化 | 真实原因、重试或权限下一步 | 错误只用短暂 toast 一闪而过 |
| 取消或离开 | 按契约恢复、保留或确认草稿 | 假称可撤回已经即时保存的变更 |

## 弹窗的理由与有意例外

弹窗可以服务短而独立的必要输入、后果确认或受限编辑；字段数量和低频本身不足以证明需要模态。
复杂表单、长说明或经常参考底层内容时，可考虑页面或非模态区域；抽屉也需要任务理由。
确需模态时复用宿主组件，处理进入焦点、内部 Tab 循环、Escape、关闭后焦点与草稿保护。
不因为 APG 展示了嵌套示例，就默认在“编辑设置”里再弹“编辑字段”；优先消除重复事务。
有意例外：密钥配置需要单独显示访问范围与测试结果，可以保留摘要加配置流程，不能将真实秘密随意回显。
有意例外：公共服务一问一页有降低认知负担的理由；不把该模式机械套到每日操作的五项偏好设置。
反例：页面列出五个值，“编辑”弹出相同五个字段，而关闭后还要再点页面 Save；事务边界难以理解。
改进候选是原位五项表单与一个 Save 区，而不是给五项值分别自动保存。

## 项目化例子

例：邮件插件已有发送频率 select、签名 textarea、两个布尔字段与统一 Save。用户要减少弹窗和排版跳变。
采纳规则可写成：沿用字段与接口，四项原位显示，统一控件列和文字角色，Save 只提交本组，取消恢复上次已保存值。
标签较长时允许换行；条件项仍按原有契约保留隐藏值。提交失败在保存区持续提示，并保留草稿。
如果产品以后允许某个独立布尔项即时提交，应单独确认生效语义、失败恢复和取消边界，再更新项目规则。

## 可观察验收

- 核对修改前后字段类型、选项、精度、提交载荷和 Save 范围；视觉改进没有暗改数据语义。
- 改动多个字段后取消、失败后重试、保存后重新打开，值与项目契约一致。
- 键盘完成填写与提交，错误可定位；必要反馈可由辅助技术感知，焦点不被普通成功提示夺走。
- 用长标签、长错误、窄屏与放大检查对齐，确认错误未指向相邻字段、保存区未遮挡内容。
- 如保留弹窗，验证关闭和重新打开后的草稿、焦点与背景交互；静态截图不证明这些行为。

## 已核实的一手来源

核实日期：2026-11-11。控件语义与错误恢复来自下列资料；整体保存保留与原位布局是结合场景的综合建议。

- [Fluent Switch](https://fluent2.microsoft.design/components/web/react/core/switch/usage/)：即时二元变化；需要提交步骤时建议 checkbox。本文同时保留项目既有草稿开关例外。
- [GOV.UK Checkboxes](https://design-system.service.gov.uk/components/checkboxes/)：多选关系、标签与组名；其公共服务预选策略不自动覆盖已有设置值。
- [GOV.UK Validation](https://design-system.service.gov.uk/patterns/validation/)：保留输入、提供字段错误和摘要，避免尚未输入完就持续验证；不把权限判断当字段校验。
- [WAI-ARIA Modal Dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)：模态焦点、键盘及关闭后返回，不是采用模态的产品理由。
- [W3C 状态消息](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)：保存与等待反馈的程序化可感知性。
