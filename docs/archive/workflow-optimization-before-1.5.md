### 已确认的源码问题

| 问题 | 证据位置 | 影响 |
| --- | --- | --- |
| 决策失效只局部覆盖 | `dev-planner/SKILL.md` 的范围对账只检查 Spec/计划中的非目标、延期声明 | 技术选型、设计约束、临时假设和维护决策没有统一替代机制 |
| 历史与当前依据边界不清 | `dev-planner/references/stage-contract.md` 同时要求已完成只读、范围修订，并写“延续开发、验证与审查以明细为准” | 历史任务与证据可能被误当成当前有效要求；“当前 Phase 之外不可变”还可能误伤未开始计划的正常调整 |
| 没有项目现状手册契约 | 全局默认路径及开发/维护/发布输出未定义这种产物及维护责任 | Spec 表达预期，Phase 记录过程，二者都不能单独证明当前已实现、可运行或已部署状态 |
| 文档同步未进入明确交付条件 | `dev-builder` 合格标准与 `reviewer` 必查项没有受影响文档对账及旧决策替代检查 | 规划时安排了更新，执行结束仍可能遗漏；维护路线也会绕过规划对账 |
| 膨胀治理不完整 | Spec 持续追加变更记录；`batch.md` 每项追加但没有已复查条目的归档规则；计划索引永久累积全部 Phase | 拆分了单个计划文件，仍未限制默认读取的活跃信息量 |
| 规模、路线与风险绑在一起 | AGENTS 把产品 Phase、跨模块、依赖直接归入 R2；开发契约要求“不确定、验证不足”按 R2 | 阶段划分本身变成风险升级理由，普通改动可能被放大为独立审查任务 |
| Phase 有顺序但缺少明确承接契约 | 阶段模板有依赖段落，但没有强制稳定依赖 ID、所需前置成果和被替代关系 | 拆文件后仍可能无法判断为什么先做这项、前置成果是否存在，以及哪个后续阶段改变了它 |
| 同一规则存在冲突副本 | 需求 SKILL 最多 2 问，stage-contract 最多 3 问；README 将有限配置列入 R1，开发契约却禁止配置进入轻量队列 | 模型可能因读取入口不同而作出不同选择，需要统一边界与权威来源 |
| 评测未验证文档动作 | `evaluate_prompt_cases.py` 评分路由、风险、状态、问题数等字段 | 即使模型说对路线，也无法证明旧声明实际失效、手册已更新、历史证据仍完整 |

### 建议的最小文档分工

优先复用目标项目已有等价文档；不要求每个项目创建完整目录树。

| 文档 | 只负责什么 | 更新方式 |
| --- | --- | --- |
| `docs/PROJECT.md`（建议名，架构与开发现状入口） | 产品当前能力、架构概览与模块职责、当前开发位置/阻塞、常用命令及详细文档入口 | 原位更新摘要和导航；记录核验依据；详细架构、运行说明按主题下沉，入口不随历史线性增长 |
| `docs/Product-Spec.md` / Design Brief | 当前有效的目标行为、验收和设计约束 | 新决定确认时修订旧条款；待实现与已实现明确区分；长篇变更过程移出正文 |
| `docs/DEV-PLAN.md` / 活跃 Phase | 当前与下一步执行工作 | 入口保留活跃任务和历史导航；完成明细保留完整任务与证据，默认不全量读取 |
| 决策记录 / 历史区 | 重大选择为什么成立、何时被替代 | 复用已有记录；必要时使用稳定 ID、适用范围、状态、替代关系与理由；历史证据不可冒充当前规范 |

手册回答“现在实际怎样”，Spec 回答“当前要求怎样”；发现二者不同需说明是待实现、回归还是记录滞后，不能单凭代码覆盖用户要求。没有核验部署时写“未核验”，不能由本地构建成功推断已上线。

### 规模、风险与 Phase 的建议边界（2026-09-06）

三项判断分别进行：路线决定是否修订需求，规模决定计划粒度，风险决定验证及独立审查。产品变更不自动等于 R2，写 Phase 不自动触发 reviewer；维护任务也可能因实际影响达到 R2。

| 维度 | 建议规则 |
| --- | --- |
| 何时必须建/更新 Phase | 用户明确要求阶段计划；或存在需要独立验收、具有先后依赖的多个交付阶段。预计跨会话或需要交接的工作至少留持久任务；有现成相关 Phase 时先更新，不为每轮对话新建 |
| 何时用短任务 | 单一目标、边界明确、能一次实现和验收的改动；即使属于小型产品变更，也可修订需求后用短任务，不强制完整阶段模板 |
| 如何防止漏写 Phase | 达到阶段条件时，实施前落盘目标、依赖、任务和验收；执行后更新实际状态与证据。新会话若发现应有计划缺失，依据已确认信息补齐，不重做需求访谈 |
| R0 | 不改变运行或代理行为的文档、注释、格式；工作流提示词虽是 Markdown，改变执行规则时不能仅凭扩展名评为 R0 |
| R1 | 边界可说明、可局部回滚、验证可覆盖的常规行为变更或修复；触及多个文件、公共组件、开发配置或依赖版本，不单凭这些标签升级 |
| R2 | 存在具体重大风险，例如权限/隔离边界改变、敏感数据暴露、破坏性迁移、不兼容公开契约变化、关键业务正确性或广泛运行故障风险；说明受影响行为、可能后果和必要验证 |
| 未知项 | 先定位受影响调用方、数据流和已有验证。一般信息不足不直接等于 R2；若合理检查后仍无法排除具体重大影响，按 R2 处理并说明该影响。工具不可用另记验证缺口，不能靠提升等级假装已解决 |
| 子代理审查 | R0/R1 默认由当前会话验证；R2 根据具体风险进行独立审查，用户明确点名审查另行执行。不因 Phase 身份自动派遣；保持用户已有授权与禁用子代理约束 |

评级不能按改动行数判断：一行权限条件可能是 R2，跨多个文件调整普通样式仍可能是 R1。也不能只说“安全起见”，升级需给出实际触发项。

Phase 使用稳定 ID，不因文件搬迁重编号。最小承接信息：目标与验收、`depends_on`（前置 ID + 必须已有的成果）、当前状态与证据、相关需求/模块链接；有替代时注明 `supersedes` 或后续承接记录。前置 Phase 完成不意味着依赖永久满足，使用前核对所需成果是否仍存在。后继列表可从前置关系派生，不维护两套易失配的依赖表；历史实施证据保留，替代元数据可更新。

### 新会话入口与文档增长控制（2026-09-06）

- 新会话：读取项目指令 → 架构/开发现状入口 → 当前任务或 Phase 及相关模块材料 → 核对本次相关代码与命令。历史默认不全读，也不把入口摘要当成无需验证的事实。
- 建议入口正文预算约 150 行；主题文档约 300 行时检查能否按职责拆分。现场显示行数不足以衡量负担，还要检查总字节/可用时的 token 估算、重复内容和单段密度；默认入口与详细参考分别控制。这是整理触发参考，不是质量指标或机械阻塞门禁，不允许靠超长单行规避，也不能为了达标丢掉必要证据。
- 入口只保存架构摘要、当前里程碑/阻塞摘要与导航；具体模块事实以主题文档为准，任务状态以 DEV-PLAN/Phase 为准，命令以仓库脚本配置为依据。摘要变化同次同步，不复制完整状态表。
- 有足够内容时再建立 `docs/project/architecture.md`、`development.md` 或模块文件；主题过大再下沉到模块目录。不预建空文件、不按轮次或日期切碎当前知识。
- DEV-PLAN 保留活跃及必要的后续阶段；已完成阶段按里程碑/版本提供历史导航。历史索引过大也按里程碑拆分，入口不逐项列出所有旧 Phase。
- 一次变更影响架构、能力、命令、关键限制或当前里程碑时更新相应事实页及入口摘要；未影响这些内容的小改无需改入口或重写整个手册。阶段交付/归档时同步状态、依赖引用和链接。
- 保留完整历史任务与验证证据；归档只能降低默认读取量，不能删除可追溯信息。被新决定替代的旧声明从当前正文移出，历史标记替代关系，防止下一会话重新援引。

### 建议的更新协议与验证

1. 开始相关工作时先读现状入口与有效契约，再按问题读取历史；命中历史记录时检查适用范围及是否已被替代。
2. 新决定确认后，同一工作单元内修订受影响的当前条款，标记旧决定已替代及新记录链接，调整活跃计划；不能只在末尾追加相反声明。没有新产品未知项时，缺一份变更记录由 Agent 补写，不自动变成用户重做决定的理由。
3. 实施并验证后更新手册的已实现状态；仅规划中的内容不得提前写成事实。开发、修复、设计和发布各自同步其改变的部分，由 reviewer 检查相关文档差异。
4. 在阶段完成、决定替代、发布或出现重复/冲突内容时整理，不按每轮对话制造记录。活跃正文去重并移走失效内容；历史完整搬迁并保留引用，不用摘要替代必要证据。
5. 精简全局指令和技能入口中的重复规则，将详细模板按需加载；先统一权威来源、授权延续和停止条件，再调整表达。品牌人格可以保留，强制自我介绍是否仍需要是待讨论偏好，不擅自撤销。
6. 增加实际文件产物用例：旧非目标被新决定替代；设计/技术选型跨阶段改变；仅规划不冒充实现；维护完成后同步命令；归档后仍可追溯证据；新会话不复活失效决策；多阶段任务实际生成计划和依赖；小改跨文件但不无故升 R2；一行高影响改动仍识别 R2；入口超预算后拆分且引用完整。检查生成文件与引用，不只检查模型返回的路由标签。

| `src/uiContracts.test.js` 存在读源码后按正则匹配 CSS 属性、函数调用及实现写法的断言；Phase 记录常用全量测试数量作为摘要，同时也有实际浏览器证据 | 按验收行为选择测试，不把源码结构断言或通过数量当交互正确性证明。结构检查保留其适用边界；关键交互验证可观察结果。已有必要检查通过后，仅在新变更、失败或具体疑点出现时扩大/重跑 |
| 音乐站正在同时修改源码与多个规范；现有审查依赖“当前 diff + 证据” | 恢复/审查需绑定相关文件内容或提交基线、命令和环境。相关输入改变后只失效受影响的证据；其他人未提交修改不能当作本任务成果，不能假定先前的审查覆盖后来加入的修改 |

上述是结合官方原则作出的本工作流设计推导，官方并未规定 R0/R1/R2、审查轮数、Phase 状态或 Markdown 大小。下一轮行为评测建议从这些现场制作不含私有数据的小型仓库夹具，比较不同模型的文件结果、漏判/过判、恢复正确性，以及工具调用/审查次数与耗时；保持人工校准，不只检查返回 JSON。

### 样本充分性与迁移交付要求（2026-09-06）

**判断：足够启动首轮优化，不足以宣布跨模型验证完成。** 现有材料包含工作流源码、20 个路由/结构用例、一个长期演进的真实项目，以及过度分级、低估产品变化、审查无法闭合、状态混淆和文档膨胀的现场记录。缺少对同一任务在不同模型上的受控比较，以及旧文档迁移的实际产物验证。后续可在隔离夹具中补齐，不必等待用户再提供完整项目。

最低样本补充：单体 DEV-PLAN、已经拆分但缺失依赖的 Phase、已有健康现状入口、多来源冲突/缺失历史证据、存在未提交改动、迁移中断后继续、第二次迁移应无新增改动。夹具区分取自现场的结构与人工构造的边界，不把历史描述冒充完整原始文档。

**用户要求的迁移手册是新版交付物，当前本节仅定义其契约，不冒充已完成手册。** 手册需同时供用户审阅和 Agent 执行，随发布包提供，gateway 可定位；具体文件名与目录映射随最终架构确定。旧项目不只替换提示词，须单独识别文档是否已适配。当前 gateway 只验证工作流文件/版本和静态用例，没有 docs 适配步骤。

| 迁移步骤 | 手册必须规定的结果 |
| --- | --- |
| 盘点与定位 | 确认真实仓库、现有指令和文档入口、工作流版本、活跃任务及未提交修改；建立现有文件到新职责的映射，默认复用等价入口，不强制改名 |
| 判定有效性 | 区分已确认预期、当前实现、临时假设、有效决定、已替代决定、历史证据和待确认冲突；按适用范围及替代证据判断，不能只按日期或当前代码覆盖旧要求 |
| 逐文件处置 | 对每个纳入范围的旧文档给出保留、原位更新、拆分、合并、归档或待确认的去向和理由；未识别的用户自有文档保留，不因未被索引就删除 |
| 建立现状与计划入口 | 提炼已核验架构、模块、命令及限制；区分当前工作与历史导航；补回能由证据确定的 Phase 依赖及承接关系，缺证据时明确未知 |
| 拆分与归档 | 当前正文保留有效条款；完整历史任务、验收和证据搬迁并保留原 ID；更新全部受影响引用和替代链接，不用摘要替代明细，不给缺失历史编造任务或测试 |
| 对齐状态与规则 | 分开实施、验证、审查、发布状态；已授权的例外按原范围记录；历史风险和审查结论保留当时语境，不能用新评级追溯伪造通过，也不无条件重审所有历史阶段 |
| 验收与交接 | 新会话能定位现状/活跃任务/有效约束；关键内容有去向、链接可达、替代关系清晰、证据可追溯；记录实际迁移范围、剩余冲突及下一步，不能仅因文件已搬完就宣布完成 |

执行约束：用户已授权的 docs 整理可连续完成，文件名、分类和可发现事实不逐项追问；只有无法从证据消解且会改变预期行为的冲突需要最小澄清。正在被其他任务编辑的文件先隔离处理，迁移不能覆盖其新内容。默认用现有 Git 差异提供可审阅和恢复依据，不自动提交，也不另造回放引擎或重复备份目录。

升级状态须区分“工作流已安装”和“文档未迁移/部分迁移/已迁移”，不能只看 `.version` 就认定项目适配完成。部分迁移时保留新旧路径映射与可恢复进度，后续只做未完成部分；不阻塞无关工作，也不允许同时存在两个互相矛盾的当前权威入口。相关任务继续前对账其使用的文档即可，不要求每次开会话都全仓迁移。

迁移验收还须包含幂等性与中断恢复：重复运行不重复归档、不重编号、不新增相同手册、不重放已解决冲突。发布验证应确认 Codex/Claude 包及 gateway 能实际读取手册，并使用隔离旧项目夹具验证迁移后的文件结果。音乐站本身只作为只读依据；未获得新的明确授权前不得执行迁移。

## 1.4.0 计划生命周期、批处理通道与初始化修复

### 现场证据（音乐站真实案例）

音乐站 0→1 开发后 `docs/DEV-PLAN.md` 膨胀到 1712 行；reviewer 事后报告 Product-Spec 严重滞后：Spec 第 8 节与第 4 节非目标正面冲突（"不新增站内搜索"原样保留，实际 Phase 16-32 已引入 AI 曲库搜索）、9 个 D1 迁移未同步、Design-Brief 滞后 10 个 Phase。

根因三层：① 增量维护是"追加式"而非"对账式"，没有规则要求切新 Phase 前检查新范围是否与既有非目标/延期声明冲突；② "非目标"没有基线锚点，"本次"是永久的无日期承诺；③ "先不管"是开放承诺，无失效条件。

站点做过的"索引+归档"压缩把 1712 行压成 38 行摘要——明细被**总结掉**而不是**搬迁**，延续开发失去 REQ-AC 映射与验证证据。结论：归档可压缩摘要，但明细文件必须保留完整任务与验证证据，不得用摘要替代。

### 已确认的修正规则

1. DEV-PLAN 双层结构：`docs/DEV-PLAN.md` 索引（状态总览 + Phase 清单），`docs/dev-plan/phase-NN.md` 明细（七段结构 + 完成证据追加区）。
2. Phase 生命周期：当前 Phase 可变，已完成只读 + 追加证据，削减标"已废弃"。范围/非目标/延期声明不在此保护内，被承接必须修订。
3. 非目标带基线锚点并写成自失效；dev-planner 前置"范围对账"三分法，承接但无变更记录时暂停回 product-spec-builder。
4. 轻量批处理通道：R0/R1 小改由当前会话直接执行、不派子代理、记入 `docs/maintenance/batch.md`；不自动审查，收尾提醒，用户明确同意才批量复查；发布前强制清空。
5. 会话开场自我介绍，确认人设生效。
6. gateway 按技能自身安装位置检测宿主；`.version` 以释放包为准，禁止写成安装日期；发布包系统指令注入版本行。

### 用户反馈驱动的调整

- 批处理**不自动触发**：用户明确"agent 要知道但不能自动触发，合适的时候提醒 + 得到明确意图"。阈值机制取消，改为收尾提醒 + 用户点头。
- 小改**不派遣子代理**：用户最常说的话是"现在别派遣子代理"。子代理只用于用户明确要求的批量审查。
- `.version` 只记录安装日期是真实现场：音乐站 `.version` = `2026-07-19`，而 manifest 为 `1.3.0`。gateway 已写入"不得改写"规则但仍发生，本次改为硬行为（从包复制，不生成）。

### 升级机制

- 升级 = **整体替换工作流文件 + 保留运行时状态 + 冲突询问用户**，不构建回放引擎、不做哈希快照或备份目录。
- 关键事实：signals.md 升级时保留，自进化历史不会因整体替换丢失；现实中项目几乎没有自进化补丁历史，1.3→1.4 迁移直接整体替换，不自动回放旧版本补丁。
- 1.4.0 起要求本地修改工作流文件必须登记为 `已转补丁` 可回放条目（修改文件、原规则、新规则、关联用例）。将来确有补丁且与新版本冲突时，升级列出给用户重新评估，不静默应用或丢弃。

### 评测

- 行为用例 16 → 20，新增 `scope-reconciliation`、`batch-review` 类别；响应评分增加 `deferred` 字段区分"入待复查队列 / 即时验证"。

## 1.3.0 Prompt 契约与异常恢复

### 官方指南转化为工程约束

本版本依据 OpenAI 官方提示词工程资料确认并实施以下方向：

- 指令放在上下文之前，稳定规则与动态输入分层。
- 目标、范围、输出格式与停止条件写具体，减少依赖模型猜测。
- 使用 Markdown 标题和 XML 风格运行时标签隔离不同来源的数据。
- 对关键边界同时提供正例和反例，优先说明应该做什么。
- 修改 Prompt 前建立代表性用例，结构校验与 fresh Agent 行为评测分开报告。

因此 `AGENTS.md` 采用八段统一结构，11 个 Skill 采用七段统一入口；详细模板和 Examples 下沉到 `references/stage-contract.md`。`.creator/tests/prompt-cases/cases.json` 保存关键行为契约，`.creator/scripts/evaluate_prompt_cases.py` 负责静态检查并可评分 fresh Agent 的结构化响应。

### 1.2.0 现场事件与根因

实际长任务在多轮终审阶段停止，界面明确显示：`Selected model is at capacity. Please try a different model.`

- **直接原因**：所选模型达到容量上限，属于平台外部中断；不是业务测试失败，也不是 reviewer 给出的不通过结论。
- **工作流放大因素**：当时已累计大量子智能体完成记录，并出现重复终审。1.2.0 只要求 R2 fresh reviewer，没有规定同一 diff 去重、最大复审轮次和容量中断后的恢复动作。
- **不能得出的结论**：不能仅凭这次事件认定 1.2.0 Prompt 本身让 Agent 主动停止，也不能把切换模型当作对重复审查设计的修复。

### 已确认的修正规则

1. 审查输入用“契约版本 + diff + 验证证据”形成稳定指纹；同一指纹只运行一个 fresh reviewer。
2. reviewer 首轮一次列全问题，实施者批量修复；新 diff 最多一次聚焦复审。
3. 同一阻塞问题连续两轮仍存在，停止继续生成 reviewer，报告实现、契约或环境阻塞。
4. 模型容量、网络、工具或宿主故障标记为“中断”，不算审查轮次。
5. 中断时保存恢复检查点：原因、已完成内容、当前 diff、最后成功验证、未完成动作、恢复命令。
6. 恢复后只继续未完成步骤；短工具调用可重试一次，长期测试和 reviewer 不盲目重跑。

### 评测决策

- 当前用例集包含 16 个行为案例，覆盖 routing、questioning、visual-routing、review-convergence、interruption-recovery、evolution 和 release-boundary。
- 无 `--responses` 时只验证 Prompt 源结构、用例字段和界面元数据。
- fresh Agent 响应必须只看到原始请求和当前发布包，不能泄露期望答案；评分时检查路线、风险、主技能、追问数量、升级状态和新增 reviewer 数量。
- 响应评分默认要求覆盖全部用例；`--allow-partial` 仅用于探索性抽样，不作为全量回归门禁。
- 发布包必须携带用例与评测脚本，并在 Codex/Claude Code 的真实解包目录中验证可运行，避免自进化规则引用源码仓库才有的资产。
- Prompt 资产放入工作流专属 `.creator/`，不占用用户项目的 `tests/` 与 `scripts/`；gateway 更新时按 case ID 合并，冲突项必须确认，保留项目累积的自进化用例。
- 每次自进化补丁至少新增或关联一个行为用例，防止同类失败回归。

### 本次验证留痕

- 两个 fresh Agent 在不读取期望答案的前提下抽样处理 8 个原始请求，最终 8/8 通过结构化评分。首轮暴露的差异促使修正了“追问却标 continue”“当前请求本身已构成发布授权”等错误 fixture，并明确 `dev-builder`/`bug-fixer` 与子步骤/整体阻塞的边界。
- fresh reviewer 首轮发现 4 项：发布包缺运行时评测资产、产品变更入口重叠、响应子集可误报通过、reviewer 模板漏“中断”。四项均已修复并建立反向检查。
- 唯一一次聚焦复审确认上述四项修复，同时发现新增资产可能与用户项目根路径冲突。最终将资产迁入 `.creator/`，gateway 增加冲突检测、按 case ID 合并、静默覆盖禁令和安装后评测。
- 按“两轮后停止继续生成 reviewer”的收敛规则，没有启动第三轮 reviewer。最终相邻修复由 Python 3.6 构建、两平台真实解包评测、gateway 结构校验、严格 YAML、Markdown 链接和 diff 检查覆盖；交接时必须如实披露这一审查边界。

## 1.2.0 决策结论

- 主 Agent 中文名为“创造者”，英文名采用 **Creovator**（Creator + Innovator）。仓库名和 Skill 名继续使用 `creator`，避免破坏兼容性。
- 人格文案必须落到执行动作：拆分表面诉求与真实目的，识别用户、场景、成功证据、约束和非目标，并区分已确认、合理推断和尚待确认。
- 每轮优先追问 1～2 个会改变方向、范围或验收方式的问题；信息足够后停止追问。
- AI 不是所有产品的默认目标，只在价值、成本与错误边界合理时采用。
- reviewer 采用 R0/R1/R2 分级；R2 和产品 Phase 交付要求 fresh reviewer。
- 设计规范不再从审美词映射固定皮肤，而是记录“意图 → 决策 → 参数 → 理由/代价 → 验证检查点”。
- `release-builder` 按仓库事实识别技术生态，不默认 npm，也不在未授权部署时声称完成在线验证。
- 发布包以 `.creator-manifest.json` 声明平台、版本和技能清单；gateway 保留语义版本与已有自进化台账。

## 三路由架构

用户已确认用以下三条路线替代原来的单线流程：

1. **0→1 产品**：新产品、目标用户、价值主张或核心范围未确定。生成 Product Spec；涉及界面时生成 Design Brief；再形成完整 DEV-PLAN。
2. **产品变更**：已有产品新增能力，或改变用户可见行为、公开契约、数据、权限、流程。只维护增量需求、影响分析和增量计划，不重写无关章节。
3. **维护执行**：修复既定行为、测试/CI、内部重构、文档和依赖维护。允许在没有 Product Spec 或 DEV-PLAN 时启动，但执行前必须建立维护任务契约。

维护任务契约包含：目标/预期行为、现象与证据、范围、非目标、完成证据/验证命令、R0/R1/R2 风险级别。

以下情况必须由维护执行升级到产品变更：

- 正确行为无法从现有代码、测试、文档或用户说明中确定。
- 修改公开 API、CLI 行为、用户配置契约、持久化格式、公开数据模型、权限、安全边界或用户流程。
- 修复需要用户在多个合理行为之间做产品选择。
- 原任务表述为“优化/重构”，实际却扩大用户可见范围。

R0/R1 的短契约可以保留在当前会话；R2、跨会话、多阶段或多人协作任务写入 `docs/maintenance/<task-id>.md`。

## 自进化闭环

- 安装时生成信号台账。
- 用户纠正、测试/审查失败、规则冲突和重复人工绕行会在安全检查点被采集。
- 普通信号首次进入“观察中”，同类累计 3 次转“待处理”；安全、隐私、数据损坏、错误发布和越权事件单次直达。
- 补丁优先修改、合并或删除旧规则；只有现有结构无法覆盖时新增规则。
- 改变主流程、审查标准、安全边界或多个 Skill 的补丁必须先确认。

## 已修正的结构缺陷

- Codex 与 Claude Code 发布包都预建对应的 evolution/signals.md。
- 信号台账拥有稳定字段、合并键、严重度和状态；不再把用户沉默视为满意证据。
- 产品文档默认路径统一到 `docs/`，同时兼容旧项目根目录。
