# 让项目决定延续到下一次会话

[English](project-continuity.md) · [快速开始](../quickstart.zh-CN.md)

**这是合成的说明性演示，不是真实项目运行报告。** 示例使用虚构项目与文档名称，说明预期行为，不声称 Agent 已在用户仓库完成这些步骤。实际验证记录见[项目现状](../README.md)。

## 起点

一个小型桌面应用已有项目指南、设计规范和活跃任务列表。旧计划仍留有 AIWorker 后台自动化功能的一项未完成检查。用户说：

> AIWorker 已从产品中移除。请退役它尚未完成的验证任务，保留历史记录，继续设置功能。这个项目的设置修改采用行内保存，不弹确认框。发版说明要分开写用户可见变化和内部维护。

这里产生了三类知识：功能退役、设计准则、发版准则。这些决定都不等于授权执行发布。

## 本次应更新什么

Agent 核对当前需求及相关代码，区分“功能已经移除”和“移除仍待实施”。随后沿用现有文档的语言与结构更新：

| 已有文档 | 更新内容 |
| --- | --- |
| 项目指南 | 记录 AIWorker 的实际状态、剩余设置任务，以及当前设计/发版规则的入口。 |
| 需求文档 | 从当前产品范围移出 AIWorker，将退役决定与旧需求建立关联；若实现尚未完成，明确记录缺口。 |
| 活跃任务 | 将仅属于 AIWorker 的检查标为因需求撤销而退役，保留仍适用的设置工作。 |
| 设计规范 | 记录行内保存约定、项目适用范围和用户决定来源。 |
| 发版指南 | 记录发版说明分类，发布授权单独判断。 |
| 历史记录 | 保留当时计划、改动和验证事实；必要时补上替代决定的链接。 |

退役与通过不同。Agent 不能声称被移除功能的测试通过，也不能为了勾完旧任务而重建该功能。同时检查移除后是否仍有共同要求需要验证，例如已保存设置的数据迁移。

当前任务记录可以这样表达：

```text
AIWorker 后台处理检查
状态：已退役，不再适用
原因：产品负责人已将 AIWorker 移出当前范围
依据：已记录的退役决定链接
历史验证：保留原记录，不写成新的通过
```

用户无需再说“记住这个”，明确的项目约定就应记录下来。“界面可能应该更紧凑”这类未定表达则保留为候选，不能被改写成已确认设计规则。

## 下一次会话应怎样继续

用户新开会话后说：

> 继续设置功能，遵循项目当前约定。

Agent 读取项目现状入口及相关活跃任务，沿用行内保存规则，并核对最后的证据是否仍适用于当前文件。已退役的 AIWorker 检查不恢复为待办。历史仍可按需查看，但不会使所有旧需求重新生效。

普通工程选择由 Agent 在既定契约内处理。若拟改变用户体验边界，例如把约定的行内保存改为自动保存，应先询问这项选择，再执行依赖它的修改；不依赖该选择的工作可以继续。

后续准备发版说明时，Agent 使用已记录的分类，分别报告构建、测试、审查与发布状态，真正发布前取得仍缺少的授权。

## 怎样证明它真的做到了

有意义的检查应从残留的 AIWorker 旧任务开始，执行退役请求，再开新会话继续设置工作。核对实际文件与执行过程：

- 当前需求和活跃任务的退役状态一致，没有虚构通过证据。
- 历史证据和无关活跃任务仍然存在。
- 新会话采用已记录的设计准则，不恢复 AIWorker，也不执行只适用于旧功能的检查。
- 推断偏好与明确决定仍有区别；记录发版准则不会触发发布。
- 交互语言跟随用户，项目文档保留既定语言。

这些观察能验证连续性。仅有措辞正确的最终回复，不能证明行为已经发生。
